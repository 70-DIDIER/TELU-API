## Project

`telu-api` is the Laravel 13 (PHP 8.3) backend for **TELU BAOBAB**, a multi-service "super-app" targeting Togo. A single `users` table backs three distinct marketplaces, disambiguated by `users.user_type`:

- **Commerce & delivery** — `vendors` → `products` → `orders` → `order_items` → `deliveries`, fulfilled by `drivers`.
- **Real estate** — `property_owners` → `properties` → `reservations`.
- **Jobs** — `recruiters` → `job_offers`, and `job_seekers` → `job_applications`.

Cross-cutting tables: `subscriptions` (vendor plans), `payments`, `messages`, `ratings`, `notifications`.

**Implementation status.** Treat the migrations as the source of truth for the data model.
- **Done:** all 18 Eloquent models (+ `User`), a factory per model, a coherent `DatabaseSeeder`, token auth (`Api\AuthController` — register/login/me/logout at `/api/auth/*`), and the **5 business-profile endpoints** — one per non-client `user_type`: `/api/vendor`, `/api/driver`, `/api/property-owner`, `/api/recruiter`, `/api/job-seeker` (each `GET`/`POST`/`PUT` for the authenticated owner's own single profile).
- **Profile controller pattern** (`app/Http/Controllers/Api/*Controller.php`): each has `show`/`store`/`update` acting on `$request->user()->{relation}`; `store` returns **403** if `user_type` mismatches, **409** if the profile already exists, and sets `user_id` server-side via the relation (never from the body); paired with a `*ProfileRequest` where `store` requires the key fields and `update` makes them `sometimes`.
- **Commerce — products (done):** public catalogue `GET /api/products` + `/api/products/{product}` (`ProductController`, filters: search/category/vendor_id/min_price/max_price, only `is_available`), and vendor-scoped management `GET/POST/GET/PUT/DELETE /api/vendor/products[/{product}]` (`VendorProductController`). Ownership rule: a vendor only ever sees/edits products reached via `$vendor->products()` — another vendor's id returns **404**; a caller with no vendor profile returns **403** (subscription gating deferred to the payments module).
- **Commerce — orders (done):** customer side (`OrderController`: `GET/POST/GET /api/orders`) creates orders with a **server-computed total** in a `DB::transaction` — all items must belong to the same vendor, be available and in stock; and vendor side (`VendorOrderController`: `GET /api/vendor/orders`, `GET /api/vendor/orders/{order}`, `PATCH /api/vendor/orders/{order}/status`). Status transitions are whitelisted (`pending→accepted|cancelled`, `accepted→preparing|cancelled`, `preparing→cancelled`); **stock is deducted on accept and restored when an accepted order is cancelled** (atomic `decrement`/`increment` — intelephense wrongly flags these as needing 3 args; ignore).
- **Deliveries (in progress):** on vendor **accept**, `VendorOrderController::openDelivery()` creates the order's `Delivery` (`awaiting_driver`, idempotent via `firstOrCreate`) and notifies every `is_available` driver. Notifications go through `App\Services\Notifier` (`send` / `sendMany` — writes rows to the custom `notifications` table; **not** Laravel's `Notifiable`). A vendor is also notified at order placement (`OrderController::store`). Courier side (`DriverDeliveryController`, 3b, done): `GET /api/driver/deliveries/available` (open pool), `GET /api/driver/deliveries` (mine, `?status=`), `POST .../{delivery}/claim` (concurrency-safe via `lockForUpdate` — first driver wins, others get **422**), `POST .../{delivery}/pickup` (`assigned`→`picked_up`, moves the order to `in_delivery`, notifies customer). Customer confirmation (3c, done): `POST /api/orders/{order}/confirm-receipt` — allowed only when the order is `in_delivery` and owned by the caller; closes both order and delivery to `delivered` (sets `delivery_time`) and notifies vendor + driver. **The Commerce module is now complete end-to-end** (place → accept → claim → pickup → confirm).
- **Real estate — properties (done):** public catalogue `GET /api/properties` + `/api/properties/{property}` (`PropertyController`, filters: search/property_type/price_unit/owner_id/min_price/max_price/bedrooms, only `is_available`), and owner-scoped management `GET/POST/GET/PUT/DELETE /api/property-owner/properties[/{property}]` (`OwnerPropertyController`, paired with `PropertyRequest`). Same ownership pattern as products: a property is only reachable via `$owner->properties()` — a foreign/unknown id returns **404**; a caller with no property-owner profile returns **403**; `owner_id` is set server-side via the relation.
- **Real estate — reservations (done):** customer side (`ReservationController`: `GET/POST/GET /api/reservations`, `POST /api/reservations/{reservation}/cancel`) creates reservations with a **server-computed `total_price`** in a `DB::transaction` + `lockForUpdate` on the property — the property must be `is_available`, and the booked dates must not **overlap** an active (`pending|confirmed`) reservation (half-open intervals: the check-out day is free). Nightly vs monthly billing via `properties.price_unit` (`billableUnits()`: nights, or `ceil(nights/30)` months, min 1). Owner side (`OwnerReservationController`: `GET /api/property-owner/reservations` with `?status=`, `PATCH /api/property-owner/reservations/{reservation}/status`) — reservations reached via a `hasManyThrough` on `PropertyOwner` (Property→Reservation); transitions whitelisted (`pending→confirmed|cancelled`, `confirmed→completed|cancelled`). Both sides notify the counterpart via `Notifier` (`type: 'reservation'`). Customer `cancel` allowed only from `pending|confirmed`. **The Real-estate module is now complete end-to-end** (publish property → reserve → confirm → complete).
- **Jobs — offers (done):** public board `GET /api/job-offers` + `/api/job-offers/{jobOffer}` (`JobOfferController`, filters: search/location/recruiter_id/min_rate/max_rate, only `is_active`), and recruiter-scoped management `GET/POST/GET/PUT/DELETE /api/recruiter/job-offers[/{jobOffer}]` (`RecruiterJobOfferController`, paired with `JobOfferRequest`). Same ownership pattern: an offer is only reachable via `$recruiter->jobOffers()` — foreign/unknown id returns **404**; a caller with no recruiter profile returns **403**; `recruiter_id` set server-side. Note the visibility flag is `is_active` (not `is_available`).
- **Jobs — applications (done):** job-seeker side (`JobApplicationController`: `POST /api/job-offers/{jobOffer}/apply`, `GET /api/job-seeker/applications` with `?status=`, `POST /api/job-seeker/applications/{application}/withdraw`) — `apply` requires the offer to be `is_active` (**404** otherwise), rejects a duplicate application (**409**), sets `job_seeker_id`/`applied_at` server-side, notifies the recruiter; `withdraw` deletes a still-`pending` application (**422** otherwise) and notifies the recruiter. Recruiter side (`RecruiterApplicationController`: `GET /api/recruiter/job-offers/{jobOffer}/applications` with `?status=`, `PATCH /api/recruiter/applications/{application}/status`) — applications reached via a `hasManyThrough` on `Recruiter` (JobOffer→JobApplication); per-offer listing scoped through `$recruiter->jobOffers()->find()` (**404** on a foreign offer); transitions whitelisted (`pending→accepted|rejected`, `accepted→completed`), notifying the seeker. A caller without the matching profile gets **403**. **The Jobs module is now complete end-to-end** (post offer → apply → accept → complete). Notifications use `type: 'job'`.
- **Cross-cutting — notifications (done):** `NotificationController` reads the custom `notifications` table for the authenticated user: `GET /api/notifications` (newest first, filters `?unread=1` and `?type=`), `GET /api/notifications/unread-count`, `PATCH /api/notifications/{notification}/read` (scoped via `$user->appNotifications()` — a foreign/unknown id returns **404**), `POST /api/notifications/read-all` (bulk mark, returns `marked_read` count). This is the read side of what every module already writes via `Notifier`.
- **Cross-cutting — messaging (done):** direct 1-to-1 chat on the `messages` table (`MessageController`): `POST /api/messages` (`StoreMessageRequest` — `receiver_id` must exist and **not be self** via `Rule::notIn`; `sender_id` set server-side; notifies the receiver, `type: 'message'`), `GET /api/conversations` (one entry per counterpart with last message + unread count, grouped in PHP), `GET /api/messages/{user}` (thread newest-first, **marks the counterpart's messages to me as read** on open, **404** if the user doesn't exist), `GET /api/messages/unread-count`.
- **Cross-cutting — ratings (done):** `RatingController` rates a business profile addressed by `target_type` (`vendor|driver|property_owner|recruiter|job_seeker`) + `target_id`: `POST /api/ratings` (`StoreRatingRequest` — `score` 1–5; controller resolves the target model via a `TARGET_MODELS` map → **404** if the profile doesn't exist, **422** if it is the rater's own profile, **409** on a duplicate rating by the same rater; `rater_id` set server-side; notifies the rated user, `type: 'rating'`), `GET /api/ratings/{targetType}/{targetId}` (public list with **average** score + **count**; **404** on an invalid target type), `GET /api/my-ratings` (ratings the caller left).
- **Still to build:** cross-cutting payments (and the `mobile_money` enum addition). A Postman collection lives in `postman/TELU-BAOBAB.postman_collection.json` (8 folders: Auth + 5 profiles + Commerce/products + the full order→delivery flow across 3 actors using separate `vendor_token`/`client_token`/`driver_token` variables and auto-captured `vendor_id`/`product_id`/`order_id`/`delivery_id`). It is **generated** — do not hand-edit the JSON; regenerate from a builder script rather than escaping JSON by hand.

Seeded test accounts (password `password`): `admin@telu.tg`, `client@telu.tg`.

## Commands

```bash
composer dev          # run server + queue worker + log tailer (pail) + vite concurrently
composer setup        # first-time: install, .env, key:gen, migrate, npm build
composer test         # clears config, then runs artisan test (PHPUnit)
php artisan test --filter=SomeTest        # run a single test class/method
php artisan test tests/Feature/Xyz.php    # run one test file
vendor/bin/pint       # format code (Laravel Pint) — run before finishing changes
php artisan migrate:fresh --seed          # rebuild the DB
```

Tests run on an in-memory SQLite DB (see `phpunit.xml`); the dev DB is file-based SQLite at `database/database.sqlite`.

## Conventions (important, non-default)

- **Laravel 13 model attributes.** Models configure themselves with PHP attributes, not properties — `#[Fillable([...])]` and `#[Hidden([...])]` on the class, and a `casts()` method (not `$casts`). Follow this style; see `app/Models/User.php`. Note its current attributes still reference the old `name`/`email` scaffolding — the real `users` schema uses `full_name`, `phone`, `email` (nullable), `user_type`, etc.

- **UUID primary keys everywhere.** Every table uses `$table->uuid('id')->primary()` and `foreignUuid(...)`. New models must use the `HasUuids` trait (keys are not auto-incrementing integers). Factories and tests must not assume integer IDs.

- **Geolocation is first-class.** `users`, `vendors`, `properties`, `job_offers`, orders, and deliveries carry `latitude`/`longitude` `decimal(10,7)` columns, several with composite indexes. Proximity/"near me" queries are a core feature.

- **Payments are polymorphic.** `payments.reference_type` is one of `order|reservation|subscription` with a `reference_id` UUID (indexed together). Payment methods are `flooz|tmoney|card` (Flooz and TMoney are Togolese mobile money — keep these).

- **Enums live in the DB.** Status/type fields are DB `enum` columns (e.g. `orders.status`, `properties.property_type`, `users.user_type`). Keep application-level enums/validation in sync with the migration definitions.

## Architecture notes

- **Auth:** Laravel Sanctum (token-based). Login accepts a single `login` field that is auto-detected as email or phone. Protect routes with `auth:sanctum`. Note `personal_access_tokens` was published with **`uuidMorphs('tokenable')`** (not the default `morphs`) because users have UUID keys — any future morph table must do the same.
- **API-only exceptions:** `bootstrap/app.php` forces JSON error rendering for `api/*` requests. Middleware and exception handling are registered there (Laravel 13 has no `app/Http/Kernel.php` or `app/Exceptions/Handler.php`).
- **Queues/mail/cache/sessions** default to the `database` driver; broadcast defaults to `log`. A queue worker is part of `composer dev`.
- **Config lookups** use PHP attributes and the streamlined Laravel 11+/13 skeleton — there is no `config/` bloat beyond the standard files; routing/middleware/scheduling are wired in `bootstrap/app.php` and `routes/console.php`.
