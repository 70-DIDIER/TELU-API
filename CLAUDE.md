
# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`telu-api` is the Laravel 13 (PHP 8.3) backend for **TELU BAOBAB**, a multi-service "super-app" targeting Togo. A single `users` table backs three distinct marketplaces, disambiguated by `users.user_type`:

- **Commerce & delivery** — `vendors` → `products` → `orders` → `order_items` → `deliveries`, fulfilled by `drivers`.
- **Real estate** — `property_owners` → `properties` → `reservations`.
- **Jobs** — `recruiters` → `job_offers`, and `job_seekers` → `job_applications`.

Cross-cutting tables: `subscriptions`, `wallets` + `wallet_transactions`, `withdrawal_requests`, `settings`, `payments`, `messages`, `ratings`, `notifications`, `addresses`.

**Monetisation is split by module, don't confuse the two mechanisms:**
- **Commerce & delivery are commission-based**, never subscription-based. `vendors`/`drivers` have **no** `subscription_id` — every delivered-and-paid order automatically credits the vendor's and the driver's `Wallet` (net of a platform commission), via `App\Services\CommerceLedger`. See the wallets bullet below.
- **Real estate & jobs are subscription-based**. Only `property_owners` and `recruiters` have `subscription_id`/`subscription_started_at`/`subscription_expires_at` and `subscriptions.subscriber_type` only accepts `property_owner|recruiter`. An active subscription lifts a free-listing quota and boosts the listing (`is_featured`, sorted first) — see the subscriptions bullet below. Do not reintroduce vendor/driver as subscriber types; that was tried and rolled back (`2026_08_10_000001_remove_subscription_from_vendors_and_drivers.php`) because nothing ever gated on it.

**Implementation status.** Treat the migrations as the source of truth for the data model.
- **Done:** all 18 Eloquent models (+ `User`), a factory per model, a coherent `DatabaseSeeder`, token auth (`Api\AuthController` — register/login/me/logout at `/api/auth/*`), and the **5 business-profile endpoints** — one per non-client `user_type`: `/api/vendor`, `/api/driver`, `/api/property-owner`, `/api/recruiter`, `/api/job-seeker` (each `GET`/`POST`/`PUT` for the authenticated owner's own single profile).
- **Profile controller pattern** (`app/Http/Controllers/Api/*Controller.php`): each has `show`/`store`/`update` acting on `$request->user()->{relation}`; `store` returns **403** if `user_type` mismatches, **409** if the profile already exists, and sets `user_id` server-side via the relation (never from the body); paired with a `*ProfileRequest` where `store` requires the key fields and `update` makes them `sometimes`.
- **Commerce — products (done):** public catalogue `GET /api/products` + `/api/products/{product}` (`ProductController`, filters: search/category/vendor_id/min_price/max_price, only `is_available`), and vendor-scoped management `GET/POST/GET/PUT/DELETE /api/vendor/products[/{product}]` (`VendorProductController`). Ownership rule: a vendor only ever sees/edits products reached via `$vendor->products()` — another vendor's id returns **404**; a caller with no vendor profile returns **403**. No quota/gating here — vendors are commission-based, not subscription-based (see the monetisation note above).
- **Commerce — orders (done):** customer side (`OrderController`: `GET/POST/GET /api/orders`) creates orders with a **server-computed total** in a `DB::transaction` — all items must belong to the same vendor, be available and in stock. `total_amount = products subtotal + delivery_fee`; `delivery_fee` is distance-based (`OrderController::calculateDeliveryFee()`: `delivery_base_fee + distance_km × delivery_rate_per_km`, bounded by `delivery_min_fee`/`delivery_max_fee`, all `Setting::get()` — falls back to the floor fee if either point lacks GPS coordinates), and `commission_amount`/`vendor_net_amount` are computed from `commission_rate_order` at the same time (stored on the order, not just derived). Vendor side (`VendorOrderController`: `GET /api/vendor/orders`, `GET /api/vendor/orders/{order}`, `PATCH /api/vendor/orders/{order}/status`). Status transitions are whitelisted (`pending→accepted|cancelled`, `accepted→preparing|cancelled`, `preparing→cancelled`); **stock is deducted on accept and restored when an accepted order is cancelled** (atomic `decrement`/`increment` — intelephense wrongly flags these as needing 3 args; ignore).
- **Deliveries (done):** on vendor **accept**, `VendorOrderController::openDelivery()` creates the order's `Delivery` (`awaiting_driver`, idempotent via `firstOrCreate`), copying `delivery_fee` from the order and computing `commission_amount`/`driver_net_amount` from `commission_rate_delivery`, and notifies every `is_available` driver. Notifications go through `App\Services\Notifier` (`send` / `sendMany` — writes rows to the custom `notifications` table; **not** Laravel's `Notifiable`). A vendor is also notified at order placement (`OrderController::store`). Courier side (`DriverDeliveryController`): `GET /api/driver/deliveries/available` (open pool), `GET /api/driver/deliveries` (mine, `?status=`), `POST .../{delivery}/claim` (concurrency-safe via `lockForUpdate` — first driver wins, others get **422**), `POST .../{delivery}/pickup` (`assigned`→`picked_up`, moves the order to `in_delivery`, notifies customer). Customer confirmation: `POST /api/orders/{order}/confirm-receipt` — allowed only when the order is `in_delivery` and owned by the caller; closes both order and delivery to `delivered` (sets `delivery_time`), notifies vendor + driver, and calls `CommerceLedger::settleOrderIfReady()` (see the wallets bullet). **The Commerce module is complete end-to-end** (place → accept → claim → pickup → confirm → wallets settled).
- **Real estate — properties (done):** public catalogue `GET /api/properties` + `/api/properties/{property}` (`PropertyController`, filters: search/property_type/price_unit/owner_id/min_price/max_price/bedrooms, only `is_available`, sorted with active-subscriber listings first), and owner-scoped management `GET/POST/GET/PUT/DELETE /api/property-owner/properties[/{property}]` (`OwnerPropertyController`, paired with `PropertyRequest`). Same ownership pattern as products: a property is only reachable via `$owner->properties()` — a foreign/unknown id returns **404**; a caller with no property-owner profile returns **403**; `owner_id` is set server-side via the relation. **Subscription-gated:** an owner without an active subscription (`PropertyOwner::hasActiveSubscription()`, via `App\Concerns\HasSubscription`) can only publish up to `Setting::get('property_free_quota', 3)` properties — `store()` beyond that returns **403**; `Property::getIsFeaturedAttribute()` mirrors the owner's active-subscription state and drives the sort-first boost above.
- **Real estate — reservations (done):** customer side (`ReservationController`: `GET/POST/GET /api/reservations`, `POST /api/reservations/{reservation}/cancel`) creates reservations with a **server-computed `total_price`** in a `DB::transaction` + `lockForUpdate` on the property — the property must be `is_available`, and the booked dates must not **overlap** an active (`pending|confirmed`) reservation (half-open intervals: the check-out day is free). Nightly vs monthly billing via `properties.price_unit` (`billableUnits()`: nights, or `ceil(nights/30)` months, min 1). Owner side (`OwnerReservationController`: `GET /api/property-owner/reservations` with `?status=`, `PATCH /api/property-owner/reservations/{reservation}/status`) — reservations reached via a `hasManyThrough` on `PropertyOwner` (Property→Reservation); transitions whitelisted (`pending→confirmed|cancelled`, `confirmed→completed|cancelled`). Both sides notify the counterpart via `Notifier` (`type: 'reservation'`). Customer `cancel` allowed only from `pending|confirmed`. **The Real-estate module is now complete end-to-end** (publish property → reserve → confirm → complete).
- **Jobs — offers (done):** public board `GET /api/job-offers` + `/api/job-offers/{jobOffer}` (`JobOfferController`, filters: search/location/recruiter_id/min_rate/max_rate, only `is_active`, sorted with active-subscriber offers first), and recruiter-scoped management `GET/POST/GET/PUT/DELETE /api/recruiter/job-offers[/{jobOffer}]` (`RecruiterJobOfferController`, paired with `JobOfferRequest`). Same ownership pattern: an offer is only reachable via `$recruiter->jobOffers()` — foreign/unknown id returns **404**; a caller with no recruiter profile returns **403**; `recruiter_id` set server-side. Note the visibility flag is `is_active` (not `is_available`). **Subscription-gated**, same mechanics as properties: `Setting::get('job_offer_free_quota', 3)` free offers, then **403**; `JobOffer::getIsFeaturedAttribute()` drives the boost.
- **Jobs — applications (done):** job-seeker side (`JobApplicationController`: `POST /api/job-offers/{jobOffer}/apply`, `GET /api/job-seeker/applications` with `?status=`, `POST /api/job-seeker/applications/{application}/withdraw`) — `apply` requires the offer to be `is_active` (**404** otherwise), rejects a duplicate application (**409**), sets `job_seeker_id`/`applied_at` server-side, notifies the recruiter; `withdraw` deletes a still-`pending` application (**422** otherwise) and notifies the recruiter. Recruiter side (`RecruiterApplicationController`: `GET /api/recruiter/job-offers/{jobOffer}/applications` with `?status=`, `PATCH /api/recruiter/applications/{application}/status`) — applications reached via a `hasManyThrough` on `Recruiter` (JobOffer→JobApplication); per-offer listing scoped through `$recruiter->jobOffers()->find()` (**404** on a foreign offer); transitions whitelisted (`pending→accepted|rejected`, `accepted→completed`), notifying the seeker. A caller without the matching profile gets **403**. **The Jobs module is now complete end-to-end** (post offer → apply → accept → complete). Notifications use `type: 'job'`.
- **Jobs — public job-seeker directory (done):** the mirror of the job board for recruiters sourcing talent — `GET /api/job-seekers` (`JobSeekerController::browse`, filters `search` on `profession` and `availability`, paginated) + `GET /api/job-seekers/{jobSeeker}` (`showPublic`) — no ownership scoping, any authenticated user can browse any seeker's profile.
- **Cross-cutting — notifications (done):** `NotificationController` reads the custom `notifications` table for the authenticated user: `GET /api/notifications` (newest first, filters `?unread=1` and `?type=`), `GET /api/notifications/unread-count`, `PATCH /api/notifications/{notification}/read` (scoped via `$user->appNotifications()` — a foreign/unknown id returns **404**), `POST /api/notifications/read-all` (bulk mark, returns `marked_read` count). This is the read side of what every module already writes via `Notifier`.
- **Cross-cutting — messaging (done):** direct 1-to-1 chat on the `messages` table (`MessageController`): `POST /api/messages` (`StoreMessageRequest` — `receiver_id` must exist and **not be self** via `Rule::notIn`; `sender_id` set server-side; notifies the receiver, `type: 'message'`), `GET /api/conversations` (one entry per counterpart with last message + unread count, grouped in PHP), `GET /api/messages/{user}` (thread newest-first, **marks the counterpart's messages to me as read** on open, **404** if the user doesn't exist), `GET /api/messages/unread-count`.
- **Cross-cutting — saved addresses (done):** `AddressController` manages a user's delivery-address book on the `addresses` table (`user_id`, `label`, `address`, nullable `latitude`/`longitude`, `is_default`), used by commerce checkout: `GET/POST /api/addresses`, `PUT/DELETE /api/addresses/{address}`, `PATCH /api/addresses/{address}/default`. Ownership pattern: reached only via `$user->addresses()` — a foreign/unknown id returns **404**. **The first address a user ever creates is always the default**, regardless of the submitted flag; setting a new default (on create/update/`setDefault`) atomically unsets the previous one inside `DB::transaction`; deleting the default promotes the most recently created remaining address (if any).
- **Cross-cutting — ratings (done):** `RatingController` rates a business profile addressed by `target_type` (`vendor|driver|property_owner|recruiter|job_seeker`) + `target_id`: `POST /api/ratings` (`StoreRatingRequest` — `score` 1–5; controller resolves the target model via a `TARGET_MODELS` map → **404** if the profile doesn't exist, **422** if it is the rater's own profile, **409** on a duplicate rating by the same rater; `rater_id` set server-side; notifies the rated user, `type: 'rating'`), `GET /api/ratings/{targetType}/{targetId}` (public list with **average** score + **count**; **404** on an invalid target type), `GET /api/my-ratings` (ratings the caller left).
- **Cross-cutting — payments (done, real gateway — PayGate Global):** mobile money only, `payment_method` enum reduced to **`flooz|tmoney`** (TMoney = Mixx by Yas); `card` and `mobile_money` were dropped by a driver-aware migration (`2026_07_26_000001_…`, existing rows remapped to `flooz`). `2026_07_26_000002_…` adds `identifier` (unique, our `TELU-XXXXXXXXXXXX` reference sent to PayGate), `payment_reference` (Flooz/TMoney receipt), `phone_number` and `paid_at`; `transaction_id` now holds PayGate's `tx_reference`. `App\Services\PayGate` wraps the four endpoints (`/api/v1/pay` push USSD, `/api/v1/status`, `/api/v2/status` by identifier, `/api/v1/check-balance`) plus `paymentPageUrl()` (hosted page, method 2); it never throws on network failure — it returns `['ok' => false, 'message' => …]`, and `mapStatus()` maps PayGate codes (0 payé, 2 en cours, 4 expiré, 6 annulé) to `success|pending|failed`. Credentials live in `config/services.php` → `paygate` (`PAYGATE_API_KEY`, `PAYGATE_BASE_URL`, `PAYGATE_CALLBACK_URL`).
  `PaymentController`: `POST /api/payments` (`StorePaymentRequest` — `payment_method` in `flooz|tmoney`, `phone_number` required and normalised to the 8-digit Togolese form; **amount resolved server-side** from the referenced entity, never the body — order `total_amount` / reservation `total_price` / subscription `price`; ownership enforced for orders & reservations → **403**, missing reference → **404**; **409** if already `success`) creates a `pending` payment then fires the PayGate push — on gateway refusal the payment is marked `failed` and the response is **502** with PayGate's reason. `POST /api/payments/{payment}/check` polls PayGate for a still-`pending` payment (owner-scoped → **404**; **502** if the gateway is unreachable). `POST /api/payments/callback` is **public** (registered outside `auth:sanctum`) — PayGate's webhook body is unsigned, so it is only a trigger: the controller re-reads the authoritative status from PayGate before writing, and always answers `200 {"received": true}` (even for an unknown identifier) so PayGate stops retrying. Both paths converge on `applyGatewayStatus()`, which only ever transitions a `pending` payment and notifies the user (`type: 'payment'`). `GET /api/payments` (filters `?status=`/`?reference_type=`) and `GET /api/payments/{payment}` unchanged. Still **no subscription/gating side-effects** — payment status is recorded only. **`amount` sent to PayGate must be an integer** (XOF has no sub-unit; a PHP float like `5000.0` serialises with a decimal point and PayGate rejects it with a 400) — `PayGate::requestPayment()`/`paymentPageUrl()` take `int $amount`, `PaymentController` rounds server-side. `PayGate::post()` also tracks `lastError` (PayGate's own 4xx message, sometimes plain text) so a payload bug surfaces with its real cause instead of a generic "injoignable".
- **Cross-cutting — OTP SMS (done, AfrikSMS):** vérification du numéro de téléphone par code SMS. `App\Services\AfrikSms` wraps the gateway (`/send`, `/send_multisms`, `/solde`, `/callback_url`; business success code is **100**, not the HTTP status) and, like `PayGate`, never throws on network failure. It honours `services.afriksms.driver`: **`log`** writes the SMS to the log instead of sending (dev, no credits burnt), `http` calls the real API — missing credentials are logged and surface as a **502**, never a 500. `App\Services\OtpService` owns the lifecycle: 4-digit code by default (`random_int`, length via `OTP_LENGTH`), **hashed** in `otp_codes`, never returned in a response; throttles **1 code/60 s** and **5 codes/hour per number** (429 + `Retry-After`), **5 attempts** per code; if the SMS fails the row is deleted so the user can retry immediately. Three purposes: `registration` (public, phone has no account yet — **409** if it does) whose verification returns a one-shot `verification_token` valid 30 min, `verification` (authenticated user confirming the number already on their account → sets `is_verified` + the new `users.phone_verified_at`), and `password_reset` (public forgot-password flow, `PasswordResetController`: `POST /api/auth/password/forgot` — **404** if no account for the phone — then `/verify` → one-shot `reset_token`, then `/reset` with `password` confirmed min:8, which also **revokes every Sanctum token** of the user; token issuance/redeem is generic in `OtpService::redeemToken()`, and the `purpose` DB enum was extended by the driver-aware `2026_08_01_000001_…` migration). Routes: `POST /api/auth/otp/send|verify` + `POST /api/auth/password/forgot|verify|reset` (public, `throttle:10,1`) and `POST /api/otp/send|verify` (auth). `POST /api/auth/register` accepts an optional `otp_token`, redeemed via `OtpService::redeemRegistrationToken()`; it becomes **required** when `OTP_REQUIRED_FOR_REGISTRATION=true` (default `false` so existing clients keep working). Tuning lives in `config/otp.php`. Phone formats are normalised by `App\Support\PhoneNumber` (`local()` → 8 chiffres pour PayGate, `international()` → `228…` pour AfrikSMS).
- **All modules are now implemented.** Remaining product decision still deferred: subscription-based gating of vendors/drivers. A Postman collection lives in `postman/TELU-BAOBAB.postman_collection.json` (8 folders: Auth + 5 profiles + Commerce/products + the full order→delivery flow across 3 actors using separate `vendor_token`/`client_token`/`driver_token` variables and auto-captured `vendor_id`/`product_id`/`order_id`/`delivery_id`). It is **generated** — do not hand-edit the JSON; regenerate from a builder script rather than escaping JSON by hand.

Seeded test accounts (password `password`): `admin@telu.tg`, `client@telu.tg`.

## Commands

```bash
composer dev          # run server + queue worker + log tailer (pail) + vite concurrently
composer setup        # first-time: install, .env, key:gen, migrate, npm build
composer test         # clears config, then runs artisan test (PHPUnit)
php artisan test --filter=SomeTest        # run a single test class/method
php artisan test tests/Feature/Xyz.php    # run one test file
vendor/bin/pint       # format code (Laravel Pint) — run before finishing changes
php artisan migrate:fresh --seed          # rebuild the DB
```

Tests run on an in-memory SQLite DB (see `phpunit.xml`); the **dev DB is PostgreSQL** (`DB_CONNECTION=pgsql` in `.env`). This split matters for migrations that touch DB-level enums: on Postgres those are `varchar` + a named `CHECK` constraint (e.g. `payments_payment_method_check`), which `->change()` cannot alter, so such migrations must be **driver-aware** — raw `ALTER TABLE … DROP/ADD CONSTRAINT` on `pgsql`, `->change()` (column rebuild) on `sqlite`. See `2026_07_13_000001_add_mobile_money_to_payment_method.php` for the pattern.

## Conventions (important, non-default)

- **Laravel 13 model attributes.** Models configure themselves with PHP attributes, not properties — `#[Fillable([...])]` and `#[Hidden([...])]` on the class, and a `casts()` method (not `$casts`). Follow this style; see `app/Models/User.php`. Note its current attributes still reference the old `name`/`email` scaffolding — the real `users` schema uses `full_name`, `phone`, `email` (nullable), `user_type`, etc.

- **UUID primary keys everywhere.** Every table uses `$table->uuid('id')->primary()` and `foreignUuid(...)`. New models must use the `HasUuids` trait (keys are not auto-incrementing integers). Factories and tests must not assume integer IDs.

- **Geolocation is first-class.** `users`, `vendors`, `properties`, `job_offers`, orders, and deliveries carry `latitude`/`longitude` `decimal(10,7)` columns, several with composite indexes. Proximity/"near me" queries are a core feature.

- **Payments are polymorphic.** `payments.reference_type` is one of `order|reservation|subscription` with a `reference_id` UUID (indexed together). Payment methods are **`flooz|tmoney` only** — mobile money togolais routed through PayGate Global; there is deliberately no card/cash option, so don't reintroduce one.

- **Enums live in the DB.** Status/type fields are DB `enum` columns (e.g. `orders.status`, `properties.property_type`, `users.user_type`). Keep application-level enums/validation in sync with the migration definitions.

## Architecture notes

- **Auth:** Laravel Sanctum (token-based). Login accepts a single `login` field that is auto-detected as email or phone. Protect routes with `auth:sanctum`. Note `personal_access_tokens` was published with **`uuidMorphs('tokenable')`** (not the default `morphs`) because users have UUID keys — any future morph table must do the same.
- **API-only exceptions:** `bootstrap/app.php` forces JSON error rendering for `api/*` requests. Middleware and exception handling are registered there (Laravel 13 has no `app/Http/Kernel.php` or `app/Exceptions/Handler.php`).
- **Queues/mail/cache/sessions** default to the `database` driver; broadcast defaults to `log`. A queue worker is part of `composer dev`.
- **Config lookups** use PHP attributes and the streamlined Laravel 11+/13 skeleton — there is no `config/` bloat beyond the standard files; routing/middleware/scheduling are wired in `bootstrap/app.php` and `routes/console.php`.
